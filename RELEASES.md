# EXE release contract

Applies to Recorder, MWM and any future Tanto application. Native test fixtures and `--stage-only` do not produce distributable EXEs. Engine currently ships as a pinned component, with no standalone EXE.

Electron products set `desktop: electron` and `worker_name` in `product.json`. The gate checks matching npm/product versions, exact installed dependency versions and the committed lockfile, builds a console worker, then embeds it with Chromium and the web interface in one portable EXE. Worker and unpacked desktop intermediates stay under `.build`; `--onedir` is unavailable for this product format. Recipients need only the final EXE.

1. Update the product's `product.json` with a new SemVer version; Recorder also pins the exact reviewed Engine SHA. Keep npm and lockfile versions aligned. Add that version’s changes and outstanding acceptance to `CHANGELOG.md`. Use the requested publication channel; document gameplay gaps independently of the release label.
2. Commit the combined Engine/MWM checkout. Recorder builds also require a clean Recorder checkout. The shared builder rejects dirty source, mismatched Recorder pins, missing notes, dependency version mismatches, existing local or remote release tags and existing version directories. Both one-file and one-directory builds use these gates.
3. Run the product’s `Build.ps1` with the pinned Python build environment. MWM rebuilds native libraries. Every build runs Engine’s two entrypoints through `Test-Offline.ps1`; both desktop products also run the copied EXE’s isolated `--ui-smoke` check. No step controls or screenshots the game.
4. Review `dist/<version>/`: EXE, staged-file hashes, complete test log, desktop smoke receipt, release notes, source/dependency receipt and `SHA256SUMS.txt`. The directory is published only after all gates pass and source is rechecked. The builder creates an annotated local version tag containing the checksum-list hash. A failed candidate stays under `.build/` and is not a release.
5. Push the exact commits and the builder's annotated tag `v<version>` at the product commit recorded in `release.json`, then upload those exact files to GitHub Releases. Compare uploaded asset hashes with the local checksums before publication. A requested regular release may be marked Latest; move the previous Latest to prerelease only when requested. Never move a published tag, overwrite an asset or silently rebuild a version. A fix receives a new version; keep previous packages for rollback. A Downloads convenience copy must have the same SHA-256 as the versioned EXE.

The receipts describe offline verification only. Live-game, controller, audio and another-PC checks must be recorded separately against the EXE SHA before claiming them or promoting a stable release. User recordings/settings are external to installation and must never be deleted by an upgrade. Release builds are traceable; bit-for-bit reproducibility across machines is not promised. These EXEs are not Authenticode-signed.

Explicit user instructions can authorize an untested prerelease: pass `--skip-tests-reason` to the shared builder (Recorder exposes `-SkipTestsReason`). This skips the offline suites and packaged UI smoke run, records `not_run` with the reason and null test counts, and preserves every source/version/dependency/hash/tag gate. It is rejected for stable versions. Never infer this exception merely to save time or label earlier test results as validation of the new package.

For a focused Recorder repair, `--startup-check` (`-StartupCheck`) retains the packaged UI check while skipping broad suites. The builder runs a copied EXE from a fresh directory with Python/Engine path overrides removed. Receipts report partial validation and keep skipped suite counts null. A one-file Recorder release needs only its EXE; GitHub Releases stores supporting receipts, without a separate GitHub Packages entry or a Downloads release archive.
